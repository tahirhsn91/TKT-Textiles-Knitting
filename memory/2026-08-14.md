## ADDENDUM — Issue #25 (shared request validation middleware) implementation in progress

**Issue #25** = "no shared validate middleware" — backend routes repeat `.safeParse()` boilerplate (30 occurrences across 13 files). Fix: create a `validate(schema)` Express middleware and retrofit routes.

### Work done (branch off develop, PR implied but NOT yet opened — awaiting user request)
- **Created** `backend/src/lib/validate.ts` exporting `validateBody`, `validateParams`, `validateQuery`.
- **Design decisions (validated via runtime + typecheck):**
  - Schema param typed `z.ZodType<Output, any, any>` (zod v4: `ZodTypeDef` is NOT exported).
  - Middleware does **NOT mutate `req`** — mutating widens `req.params` to `string | string[]` for downstream handlers, breaking `idParam(req)` helpers. It only validates and returns 400 on failure; handlers cast via `req.body as unknown as z.infer<typeof schema>`.
  - Error shape: `{ error: <firstIssue.message>, details: [{field, message}] }` — `error` preserves existing client contract, `details` is additive.
  - Routes reading `req.params.id` with middleware must coerce via `String(req.params.id)` (Express 5 + custom middleware widening).
  - `idParam` in `company-info.ts` loosened to accept `Record<string, string | string[] | undefined>`.
- **Retrofitted routes (committed, typecheck clean):**
  - `df7e0dc` — middleware + company-info + unreconciled-nav
  - `6c783ac` — yarn-receipts + machine-maintenance
  - Also done: factory-maintenance (4 sites), daily-deliveries (POST/PUT).
  - Runtime verified: 400 `{error, details}` on invalid, passes valid (prev-next, company-info tested).
- **Deliberately left as-is (fallback/default patterns, not 400-errors):** `machine-maintenance.ts:39`, `factory-maintenance.ts:36` (status fallback), `machine-analytics.ts:64` (baseline fallback), `masters.ts:59` (inside `requireFields` helper).
