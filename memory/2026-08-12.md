## Bug fix (issue #130): transaction-reconcile-deleted-line
Analyzed + fixed: deleting a line in a new transaction still reconciled the deleted record. Root cause: reconcile IDs were a separate useState array set once at auto-fill, never pruned on row removal; submit sent the stale full set; backend trusted it blindly.
- Created issue #130 with reproduction + plan. Branch fix/issue-130-transaction-reconcile-deleted-line.
- Plan A (frontend): added reconcileSourceId to detailSchema + to each auto-filled row (production/receipt/delivery); reconcile set now derived from the CURRENT visible details at submit; dropped the separate top-level reconcile*Ids arrays from createPayload (backend is source of truth).
- Plan B (backend): POST /transactions derives the reconcile set from req.body.details[].reconcileSourceId (authoritative), routed by txn type code (Fabric_Production / Yarn_Receipt / Fabric_Dispatch), ignoring any separate array. New lib/reconcile-derive.ts (collectReconcileSourceIds + deriveReconcileSets) + 9 unit tests. Removed reconcileIdsSchema + unused z import.
- KEY constraint: the generated CreateTransactionBody zod STRIPS unknown detail fields, so the backend reads RAW req.body.details[] for reconcileSourceId, not the parsed details.
- Verified end-to-end in dev: 2 deliveries, posted txn with only the kept line -> only that delivery reconciled, deleted one NOT. Cleaned up test data (txn 208, deliveries 33/34; delivery 33 permanently locked after reconcile, removed via direct DB delete since reconcile is permanent).
